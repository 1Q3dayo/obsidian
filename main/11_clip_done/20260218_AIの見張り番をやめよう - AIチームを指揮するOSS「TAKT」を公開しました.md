## はじめに

皆さんはAIエージェントと一緒に開発をしていて、こんな経験はないでしょうか。

「さっき言ったことをもう忘れてるの？」

AIエージェントを使った開発は本当に便利です。コードを書いてもらう、リファクタリングを任せる、テストを作ってもらう。素晴らしい時代になったなぁと思います。しかし、使えば使うほど、ある壁にぶつかります。

AIエージェントが、言うことを聞いてくれないのです。

与えた役割を忘れる。共有した知識が抜け落ちる。一度指摘したことを、しばらくしたらまたやらかす。皆さんにも身に覚えがあるのではないでしょうか。

私もまさにこの問題に悩まされてきました。そして、この問題を解決するために「TAKT」というツールを作りました。今回はその経緯と、TAKTが何をしてくれるのかをお話しします。

## AIエージェントとの終わりなき対話

TAKTを作るに至った背景には、AIエージェントとの日々の格闘がありました。まずはその苦労話からお付き合いください。

### 「見張り番」としての日々

AIエージェントが言うことを聞かない。それを防ぐために、私がやっていたことは何だったかというと、ずっと対話し続けることでした。

コードを書いてもらうとき、やり取りの量は膨大になります。「この設計方針で書いて」と伝える。書いてもらう。レビューする。修正を依頼する。また確認する。この繰り返しです。

一つのプロジェクトだけならまだいいのです。しかし、同時に3つほどのプロジェクトを進めていると、状況は一変します。常にAIからの質問や権限の許可要求を打ち返す日々です。

あちらのプロジェクトでAIが質問してくる。こちらのプロジェクトでは権限許可を求めてくる。またあちらでは指摘したはずのことをまたやっている。

疲れてきますよね。

正直に言うと、AIに仕事を任せているはずなのに、私がAIの面倒を見ているような状態になっていました。これでは本末転倒です。

### AIに見張り番をやらせればいいのでは？

ここで、ふと思いついたのです。

「この見張り番の役割、AIにやらせればいいのでは？」

AIエージェントが書いたコードをAIがレビューする。AIが設計方針を覚えていて、逸脱していたら指摘する。人間が逐一見なくても、品質が保たれる。素晴らしいアイデアに違いありません。

ところが、話はそう簡単ではありませんでした。

AIエージェントにサブエージェントを呼び出させたり、Skillを用意して使わせたりしてみました。しかし、これがなかなかうまくいかないのです。用意したツールを使ってくれるときもあれば、完全に無視するときもある。

というか、私の場合は全然使ってくれませんでした。なんで？

AIエージェントにサブエージェントを呼び出させるアプローチも試しました。うまくいくときもあれば、うまくいかないときもあります。結局、進捗を細かく確認しなくてはいけない。そしてがっかりする。人間の見張り番がAIの見張り番に変わっただけで、結局見張っているのは自分でした。

## 解決策としてのTAKT

試行錯誤の末にたどり着いた答えは、意外とシンプルなものでした。

### 「強制力」という発想

ここで発想を変えました。

AIに「お願い」するのではなく、「強制的に」レビューさせればいいのではないか。

そもそも、なぜサブエージェントやSkillがうまく機能しなかったのかを振り返ってみましょう。あれらはすべて「AIが自分の判断で使う」ことを前提にしています。つまり、使うかどうかの決定権がAI側にあるのです。だから、使ってくれるときもあれば、使ってくれないときもある。

ピースとして「コードを書く→レビューする→修正する」という流れをあらかじめ定義して、AIエージェントがその流れに従わざるを得ないようにする。サブエージェントを呼ぶかどうかの判断をAI自身に委ねるのではなく、仕組みとして強制する。決定権をAIではなく、ピースに移すのです。

そうすれば、AIが気まぐれにレビューをスキップすることもなくなります。レビューは必ず実行される。なぜなら、ピースの中にレビューのムーブメントが組み込まれているからです。

### TAKTの誕生

というわけで、作りました。

その名も TAKT （タクト）です。

TAKTでAIエージェントのオーケストレーションをするデモなどをしている様子はコチラ↓

このあと説明をしていきますが、使いたい場合にはこちらのコマンドでインストールできます。

```
npm install -g takt
```

TAKTは「Task Agent Koordination Tool」の略で、AIエージェントのマルチエージェントオーケストレーションシステムです。名前の由来は、指揮者のタクト（指揮棒）です。オーケストラの指揮者が各楽器のパートに指示を出すように、TAKTは複数のAIエージェントに指示を出して、ピースを実行します。

TAKTではオーケストラをイメージした音楽メタファで用語を統一しています。タスク実行定義のことを「ピース」、ピース内の1ステップのことを「ムーブメント」と呼びます。一般的なワークフロー用語で読み替えるなら、ピース＝ワークフロー、ムーブメント＝ステップです。

実際の動作は次のとおりです。

## TAKTのできること

TAKTにはさまざまな機能がありますが、ここでは主要なものを順に紹介していきます。

### ピースで仕事の流れを定義する

TAKTの中核は、YAML形式で定義するピースです。

たとえば、こんなピースを定義できます。

```
name: code-review
description: コードを書いてレビューするピース
max_iterations: 10
initial_movement: write-code

personas:
  coder: ../personas/coder.md
  supervisor: ../personas/supervisor.md

movements:
  - name: write-code
    persona: coder
    edit: true
    instruction_template: |
      次のタスクを実行してください。
      {task}
    rules:
      - condition: 実装完了
        next: review
      - condition: 続行不能
        next: ABORT

  - name: review
    persona: supervisor
    edit: false
    instruction_template: |
      前のムーブメントで書かれたコードをレビューしてください。
      {previous_response}
    rules:
      - condition: 問題なし
        next: COMPLETE
      - condition: 改善が必要
        next: write-code
```

このピースでは、まず「coder」ペルソナがコードを書き、次に「supervisor」ペルソナがレビューします。レビューで問題が見つかれば「write-code」ムーブメントに戻り、修正と再レビューを繰り返します。承認されればピースが完了します。

ここでのポイントは、coderがレビューを受けるかどうかを自分で判断するのではなく、ピースとして強制されているということです。AIの気まぐれに左右されません。

注目していただきたいのは `persona` と `rules` です。 `persona` にはセクションマップで定義したペルソナのキーを指定します。セクションマップとは、ピースYAMLの冒頭にある `personas:` ブロックのことで、キーとMarkdownファイルのパスを対応付けます。ペルソナのMarkdownファイルには、そのエージェントの役割や専門性を記述します。

そして `rules` は、各ムーブメントの遷移を制御するための仕組みです。 `condition` に人間が読める条件を書き、 `next` に遷移先のムーブメント名を指定します。TAKTはこの `rules` の定義からステータス判定のプロンプトを自動生成し、エージェントの出力を解析して次のムーブメントへ遷移します。つまり、遷移の判断はAIの自由意思ではなく、ピースに定義されたルールに基づいているわけです。

ちなみに `max_iterations` はピース全体の最大繰り返し回数です。万が一レビューと修正が延々とループしてしまう事態を防いでくれます。安心ですね。

### Faceted Prompting　プロンプトの関心を分離する

TAKTの大きな特徴の一つに「Faceted Prompting」というプロンプト設計パターンがあります。

マルチエージェントの開発を進めていくと、プロンプトの管理がとにかく煩雑になります。エージェントが増えるたびにプロンプトファイルが増え、それぞれのプロンプトに役割、コーディング規約、手順、ドメイン知識、出力フォーマットが混在していく。コーディング規約を一つ変えたいだけなのに、5つも6つもあるプロンプトファイルを全部開いて修正しなければならない。あるエージェントには反映したけど別のエージェントには反映し忘れた、なんてことが日常的に起こります。プロンプトの数が増えれば増えるほど、この管理コストは膨れ上がっていきます。

Faceted Promptingは、このプロンプト管理の煩雑さを解消するために生まれました。ソフトウェアエンジニアリングの「関心の分離」をプロンプト設計に適用し、一枚岩のプロンプトを次の5つの独立した関心事に分解します。

- Persona（ペルソナ）　エージェントの役割・専門性を定義する。「誰として振る舞うか」
- Policy（ポリシー）　コーディング規約・品質基準・禁止事項を定義する。「何を守るか」
- Instruction（インストラクション）　ムーブメント固有の手順を定義する。「何をするか」
- Knowledge（ナレッジ）　ドメイン知識・アーキテクチャ情報を定義する。「何を参照するか」
- Output Contract（アウトプットコントラクト）　レポート出力のフォーマットを定義する。「どう出力するか」

それぞれが独立したMarkdownファイルとして管理され、ピースYAMLのセクションマップで組み合わせを宣言します。たとえば、 `coder` と `reviewer` という異なるペルソナが同じ `architecture` ナレッジを参照する、といった構成が可能です。コーディング規約のポリシーを一箇所変更すれば、そのポリシーを使うすべてのピースに反映されます。新しいピースを作りたいときは、既存のペルソナやポリシーやナレッジを選んで組み合わせるだけです。

Faceted Promptingの詳細については、次の記事で解説しています。

### ビルトインペルソナとカスタムペルソナ

TAKTには、すぐに使えるビルトインペルソナが用意されています。主なものを紹介しましょう。

- planner　タスクの分析と計画を担当するペルソナ
- architect-planner　タスク分析と設計計画を担当するペルソナ。コード調査や不明点の解決も行う
- coder　コードを書くことに特化したペルソナ
- ai-antipattern-reviewer　AI生成コード特有のアンチパターンを検出するレビュアー。存在しないAPIの使用や誤った仮定をチェックする
- architecture-reviewer　アーキテクチャとコード品質のレビューを担当するペルソナ
- qa-reviewer　テストカバレッジと品質保証のレビューを担当するペルソナ
- security-reviewer　セキュリティ脆弱性の評価を担当するペルソナ
- supervisor　最終検証と承認を担当するペルソナ

これらのペルソナをポリシーやナレッジと組み合わせることで、設計からコーディング、レビュー、セキュリティチェックまで、一連の開発フローを自動化できます。用途に応じて使い分けてみてください。

もちろん、ビルトインだけでは足りない場面もあるでしょう。たとえば、プロジェクト固有のルールを知っているレビュアーがいたら便利だと思いませんか。TAKTではカスタムペルソナを自分で定義することもできます。

やり方はとてもシンプルです。 `~/.takt/personas/` ディレクトリにMarkdownファイルを置くだけです。

```
# ~/.takt/personas/my-reviewer.md

あなたはセキュリティに特化したコードレビュアーです。

## 役割
- セキュリティ脆弱性をチェック
- 入力バリデーションを検証
- 認証ロジックをレビュー
```

ピースからは、セクションマップでキーとファイルパスを対応付けて参照します。

```
personas:
  my-reviewer: ~/.takt/personas/my-reviewer.md
```

たとえば、自分のプロジェクト固有のコーディング規約をポリシーとして書き、そのポリシーを知っているレビュアーをペルソナとして作ることもできます。そのレビュアーはピースの中で必ず呼び出されるので、レビューを忘れるということがありません。

### ムーブメント間のコンテキスト受け渡し

AIエージェントの「忘れっぽさ」に対して、TAKTはピース全体の設計で対処しています。

まず、ピースエンジンのテンプレート変数によって、ムーブメント間でコンテキストを受け渡すことができます。 `{previous_response}` を使えば前のムーブメントの出力をそのまま次のエージェントに渡せますし、 `{task}` で元のタスク内容をどのムーブメントからでも参照できます。ほかにも `{iteration}` でピース全体のイテレーション回数を参照したり、 `{movement_iteration}` でそのムーブメントが何回目の実行かを参照したりと、さまざまな情報をテンプレートに埋め込めます。 `{task}` や `{previous_response}` 、 `{user_inputs}` はテンプレートに書かなくても自動的に注入されるので、明示的にプレースホルダーを書く必要があるのは位置を制御したいときだけです。

つまり、個々のエージェントが文脈を覚えていなくても、ピースが文脈を運んでくれるわけです。

また、ペルソナを分けることによって、特有の専門知識によるレビューや確度の異なる処理など多角的にタスク進行が可能です。さらに、ポリシーやナレッジを共有することで、異なるペルソナであっても同じ基準やドメイン知識に基づいた判断ができます。

### 並列ムーブメント

TAKTはムーブメントの並列実行にも対応しています。たとえば、アーキテクチャレビューとQAレビューを同時に実行し、その結果を集約して次のムーブメントに進むことができます。

```
- name: reviewers
    parallel:
      - name: arch-review
        persona: architecture-reviewer
        rules:
          - condition: approved
          - condition: needs_fix
        instruction_template: |
          アーキテクチャとコード品質をレビューしてください。
      - name: qa-review
        persona: qa-reviewer
        rules:
          - condition: approved
          - condition: needs_fix
        instruction_template: |
          テストカバレッジと品質をレビューしてください。
    rules:
      - condition: all("approved")
        next: supervise
      - condition: any("needs_fix")
        next: fix
```

`all("approved")` はすべてのサブムーブメントが「approved」にマッチした場合にtrueになり、 `any("needs_fix")` はいずれかのサブムーブメントが「needs\_fix」にマッチした場合にtrueになります。複数のレビュアーが並列に動くことで、レビューの待ち時間を短縮しつつ、多角的なチェックを実現できます。

### インタラクティブモード

タスクの要件が曖昧なとき、いきなり実行するのは不安ではないでしょうか。そんなときはインタラクティブモードが便利です。

TAKTはデフォルトで対話モード（Interactive planning）として起動します。引数なしで `takt` と実行すれば、AIとの対話が始まります。最初にメッセージを渡して会話を始めることもできます。

```
# 対話モードを開始
takt

# 初回メッセージ付きで開始
takt 認証機能を実装したい

# GitHub Issueを指定して実行
takt #99
```

対話モードではAIがコードベースを調査しながら、要件の確認や提案をしてくれます。Read、Glob、Grep、Bashといったツールを使ってプロジェクトの構成を把握した上で、的確な質問を投げかけてくれるわけです。

```
対話モード - タスク内容を入力してください。コマンド: /go（実行）, /cancel（終了）

> 認証機能を実装したい

[assistant]:
認証機能の実装ですね。いくつか確認させてください。

- 認証方式はどれを想定していますか？（JWT、OAuth2、セッションベースなど）
- リフレッシュトークンは必要ですか？
  ⠙ Read src/routes/index.ts
  ✓ Read
現在のルーティング構成を確認しました。既存の /api/users エンドポイントに
認証ミドルウェアを追加する形が自然そうです。

> JWTでお願い。リフレッシュトークンも必要

[assistant]:
了解しました。JWTでリフレッシュトークン付きですね。
  ⠙ Glob **/*.ts
  ✓ Glob
  ⠙ Read src/middleware/index.ts
  ✓ Read
既存のミドルウェア構成を確認しました。次の方針でよいでしょうか。
...

> /go
```

対話の中でタスクの解像度を上げたら、 `/go` と打てばピースの実行に移ります。やめたいときは `/cancel` で抜けられます。 `/go 追加の指示` のように指示を追加することも、 `/play <タスク>` で即座に実行することも可能です。

`/go` を実行すると、まずピースの選択UIが表示されます。矢印キーで使いたいピースを選んでEnterを押してください。ピースはカテゴリごとにグループ化されており、階層的に表示されます。

```
Select piece:
  (↑↓ to move, Enter to select)

  ❯ 🎼 default (current)
    📁 Development/
    📁 Research/
    Cancel
```

次に、隔離環境で実行するかどうかを確認されます。

```
? Create worktree? (Y/n)
```

`y` を選ぶと、 `git clone --shared` による隔離環境が作成され、作業ディレクトリを汚さずにタスクを実行できます。安心ですね。

ピースの実行が完了すると、PR（プルリクエスト）を作成するかどうかを聞かれます。

```
? Create pull request? (y/N)
```

つまり、対話で要件を詰める → ピース選択 → 隔離環境の作成 → 実行 → PR作成という一連の流れが、すべて対話的に進みます。いきなり「認証機能を実装して」と投げるよりも、AIと会話して要件を詰めてから実行するほうが、結果の精度が高くなります。ぜひ試してみてください。

### パイプラインモード　CI/CDとの連携

対話モードとは逆に、人の介入なしで完全に自動実行したい場面もあります。CI/CDパイプラインでの利用がその典型です。

`--pipeline` オプションを指定すると、非対話のパイプラインモードで実行できます。ブランチ作成、ピース実行、コミット、プッシュまでを自動で行います。

```
# タスクをパイプライン実行
takt --pipeline --task "バグを修正して"

# パイプライン実行 + PR自動作成
takt --pipeline --task "バグを修正して" --auto-pr

# GitHub Issueを紐付けてPR作成
takt --pipeline --issue 99 --auto-pr
```

GitHub Actionsとの連携には [takt-action](https://github.com/nrslib/takt-action) が用意されています。Issueのコメントに `@takt` と書くだけで、TAKTが自動的にタスクを実行してPRを作成してくれます。

### セッション管理と会話の再開

TAKTにはセッションを自動的に継続する仕組みがあります。ピースの実行ログはNDJSON形式で `.takt/logs/` に保存されており、次回 `takt` を実行したときに前回のセッションから自動的に続行されます。

つまり、途中で停止してしまった場合でも、再度 `takt` を実行するだけで前回の続きから再開できるわけです。特別な操作は必要ありません。

セッションをリセットしたい場合は `takt clear` コマンドを使ってください。

### Claude CodeとOpenAI Codexの両対応

TAKTはClaude CodeだけでなくOpenAI Codexにも対応しています。プロバイダーの違いは抽象化されているので、同じピース定義でどちらのAIも使えます。

さらに、CLIをインストールしなくても、API Keyを設定すればtaktが直接Anthropic APIやOpenAI APIを呼び出すこともできます。環境変数 `TAKT_ANTHROPIC_API_KEY` や `TAKT_OPENAI_API_KEY` を設定するか、 `~/.takt/config.yaml` にAPI Keyを記述してください。

ムーブメントごとにプロバイダーやモデルを変えることもできます。たとえば、設計はOpusに任せて、実装はSonnetに任せる、といった使い分けが可能です。

```
movements:
  - name: design
    persona: architect-planner
    model: opus
    # ...

  - name: implement
    persona: coder
    model: sonnet
    # ...
```

さらに、Hybrid Codexバリアントという構成も用意されています。これは、コーディングをCodexで、レビューをClaudeで実行するハイブリッド構成です。主要なビルトインピースにはそれぞれHybrid Codexバリアントが用意されているので、 `takt switch` で切り替えるだけで使えます。

### タスクのバッチ実行

`.takt/tasks/` ディレクトリにタスクファイルを置いておけば、次のコマンドでまとめて実行できます。

```
takt run
```

これだけで、ディレクトリ内のタスクが順に処理されていきます。タスクファイルはMarkdownやYAML形式に対応しています。ファイルはアルファベット順（辞書順）に実行されるので、 `001-setup.md` 、 `002-implement.md` 、 `003-test.md` のように番号プレフィックスを付けておけば、意図した順番で実行できます。

YAML形式のタスクファイルでは、ピースやブランチの個別指定もできます。

```
task: ユーザー認証のAPIエンドポイントを実装する
piece: default
branch: feature/auth
worktree: true
```

`worktree: true` を指定すると、そのタスクは隔離環境で実行されます。タスク完了後には自動的にコミット、プッシュされ、クローンが削除されます。ブランチだけが残るので、あとは `takt list` でブランチを確認し、マージや削除ができます。

タスクは `takt add` コマンドで対話的に追加することもできます。

```
takt add
```

ここで嬉しいのは、 `takt run` でタスクを実行している最中でもタスクを追加できるということです。実行中に「あ、これもやってほしい」と思いついたら、 `takt add` で追加するか、`.takt/tasks/` にファイルを置けばよいのです。現在のタスクが完了すると、追加されたタスクも順に処理されていきます。

GitHub Issueからタスクを追加する場合は `takt add #28` のようにIssue番号を指定します。Issue番号がブランチ名に自動的に反映されるので便利です。

完了したタスクは `.takt/completed/` に自動で移動されるので、何が終わっていて何が残っているかも一目瞭然です。

### タスクの監視モード

`takt run` はその時点で `.takt/tasks/` にあるタスクをまとめて実行するコマンドですが、「タスクが追加されたら自動的に実行してほしい」と思うことはないでしょうか。

そんなときは `takt watch` を使います。

```
takt watch
```

このコマンドを実行すると、taktが常駐して `.takt/tasks/` ディレクトリを監視し続けます。タスクファイルが追加されると、自動的に検出してピースを実行してくれます。処理が終わったら次のタスクがないか再びチェックし、また新しいタスクが来るまで待機します。

止めたいときは `Ctrl+C` を押すだけです。停止時にはそれまでに処理したタスクのサマリーが表示されます。

`takt run` が「今ある分をまとめて処理」するのに対して、 `takt watch` は「来たものから順に処理し続ける」イメージです。長時間の開発セッションや、外部プロセスからタスクが追加されるようなCI/CDパイプラインとの連携にも向いています。

### タスクブランチの管理

`takt list` コマンドは、taktが作成したブランチを一覧表示し、マージや削除を対話的に行えるコマンドです。

```
takt list
```

隔離環境で実行されたタスクはブランチとして残ります。 `takt list` を使えば、各ブランチの差分を確認したり、マージしたり、不要なブランチを削除したりできます。CI/CDスクリプト向けに `--non-interactive` モードも用意されています。

### 実行レポートの自動生成

もう一つ嬉しい機能があります。ピースの実行結果は `.takt/reports/` にMarkdown形式のレポートとして自動生成されます。

どのムーブメントで何が行われたか、各エージェントがどんな出力をしたかが記録されるので、あとから振り返ることができます。「あのとき何を実装したんだっけ」と思ったときに、レポートを見ればすぐに分かるわけです。Output Contractを定義しておけば、レポートのフォーマットも統一できます。

ここまでTAKTの機能を紹介してきました。それでは、実際にTAKTを使い始める方法を見てみましょう。

## TAKTチュートリアル

実際にTAKTを使い始めるまでの流れを紹介します。

### 前提条件

TAKTを使うには、次の環境が必要です。

- Node.js 18以上
- 次のいずれか
	- Claude Code または OpenAI Codex がインストール・設定済みであること
	- Anthropic API Key または OpenAI API Key（CLIのインストールは不要）
- GitHub CLI（ `gh` ）　 `takt #N` でGitHub Issueを指定する場合に必要

Claude Codeを使う場合は、あらかじめ `claude` コマンドが動作する状態にしておいてください。API Keyを使う場合は、環境変数 `TAKT_ANTHROPIC_API_KEY` を設定するか、 `~/.takt/config.yaml` に記述してください。

### インストールと初期設定

まず、TAKTをインストールします。

```
npm install -g takt
```

どこか任意のディレクトリでTAKTを叩きます。すると、日本語や英語なのか、利用するのはClaude CodeなのかCodexなのかを確認されます。これに答えるとグローバル設定ファイル（~/.takt以下）が作成されます。

`~/.takt/config.yaml` には次のような記述があります。

```
language: ja
default_piece: default
provider: claude
model: sonnet
```

この設定で、日本語でのやり取りやデフォルトのプロバイダー、モデルが指定されます。

### ピースの作成

ビルトインピースはnpmパッケージに含まれているので、インストール直後からすぐに使えます。

カスタムピースを追加したい場合は `takt eject` でビルトインを `~/.takt/` にコピーしてから編集するか、 `~/.takt/pieces/` に新しいYAMLファイルを置きます。たとえば、シンプルなコード実装→レビューのピースを作ってみましょう。

```
name: simple-review
description: コードを書いてレビューするシンプルなピース
max_iterations: 10
initial_movement: implement

personas:
  coder: ../personas/coder.md
  supervisor: ../personas/supervisor.md

movements:
  - name: implement
    persona: coder
    edit: true
    permission_mode: edit
    instruction_template: |
      次のタスクを実行してください。
      {task}
    rules:
      - condition: 実装完了
        next: review

  - name: review
    persona: supervisor
    edit: false
    instruction_template: |
      前のムーブメントの出力をレビューしてください。
      {previous_response}
    rules:
      - condition: 問題なし
        next: COMPLETE
      - condition: 改善が必要
        next: implement
```

この定義で、実装→レビュー→修正のサイクルが自動的に回ります。各ムーブメントの `rules` に定義された条件から、TAKTがステータス判定のプロンプトを自動生成します。エージェントの出力を解析して条件に合致するルールを特定し、 `next` に従い次のムーブメントへ自動的に遷移します。承認されるまでピースは完了しません。

### タスクの実行

ピースが用意できたら、実行してみましょう。いくつかの方法があります。

```
# 対話モードで要件を詰めてから実行
takt

# GitHub Issueを指定して実行
takt #99

# タスクを直接指定して実行
takt --task "ユーザー認証のAPIエンドポイントを実装して"

# パイプラインモードで実行（CI/CD向け）
takt --pipeline --task "バグを修正して" --auto-pr
```

おすすめは `takt #99` のようにGitHub Issueを指定する方法です。Issueの内容を読み取り、計画を立て、実装し、レビューし、修正し、最終確認まで自動で進めてくれます。

実行すると、まずピースの選択と隔離環境（worktree）の作成確認が表示されます。ピースを選んでEnterを押し、worktreeを作成するかどうかを答えると、ピースが動き始めます。

実行中のターミナルには、各ムーブメントの進行状況がリアルタイムで表示されます。

デフォルトで使うピースを変えたいときは `takt switch` コマンドで切り替えられます。

```
takt switch
```

対話的にピースを選択できるので、複数のピースを用意している場合に便利です。

### プロジェクト固有の設定

プロジェクトのルートに `.takt/config.yaml` を作れば、プロジェクト固有の設定が可能です。

```
piece: simple-review
provider: claude
```

これで、そのプロジェクトではいつも `simple-review` ピースがデフォルトになります。

### ビルトインとカスタマイズ

TAKTのビルトインピースやペルソナはnpmパッケージに埋め込まれています。つまり、 `npm update -g takt` でTAKTをアップデートするだけで、ビルトインも自動的に最新版になります。更新コマンドを別途叩く必要はありません。

ビルトインをカスタマイズしたい場合は `takt eject` コマンドを使います。

```
takt eject
```

このコマンドは、ビルトインのピースやペルソナを `~/.takt/` にコピーします。コピーされたファイルを編集すれば、自分好みにカスタマイズできます。 `~/.takt/` にファイルがある場合はそちらが優先されるので、ビルトインを上書きする形になります。

セットアップはこれだけです。思ったよりも簡単ではないでしょうか。さて、実際に使ってみるとどんな変化があるのか、私の体験をお伝えします。

## 実際に使ってみた感じ

ここからは、私が実際にTAKTを使って開発してみた体験をお伝えします。

### 世界が変わった

大げさに聞こえるかもしれませんが、TAKTを使い始めてから、開発体験が一変しました。

以前は3つのプロジェクトを並行して進めるのに、常にAIの出力を確認し、質問に答え、権限を許可し、品質をチェックするという作業が必要でした。気がつくと、自分がやっていることはコードを書くことではなく、AIのお世話をすることになっていました。

TAKTを導入してからは、3つのプロジェクトそれぞれにAIエージェントチームが割り当てられているようなイメージです。各チームはピースに従って自律的に動きます。コードを書くエージェントが書き、レビューするエージェントがレビューし、問題があれば自動的に修正のループが回ります。

私がやることは、タスクを投げることと、最終的な成果物を確認することだけです。

特に大きいのは、途中の「ここはどうしますか？」「この方針で合ってますか？」というやり取りが大幅に減ったことです。ピースで方針を定義済みなので、AIはそれに従うだけです。以前は半日かけて付きっきりで進めていたような作業を、タスクとして投入してあとは待つだけ、という進め方に変わりました。

もちろん万能ではありません。ピースの設計を間違えると、期待どおりの結果にならないこともあります。しかし、ピースの改善は一度やれば次からも効くので、やればやるほど楽になっていく実感があります。

### 3つのAIエージェントチームを同時に動かす

実際の運用では、プロジェクトごとにピースとカスタムペルソナ、ポリシー、ナレッジを定義しています。

あるプロジェクトではdefaultのピース。別のプロジェクトではCQRS+ESなのでexpert-cqrsのピース。もう一つのプロジェクトでは、プロンプトエンジニアリングに特化したピース。

それぞれが独立して動いていて、私は各プロジェクトのタスクを指示するだけです。タスクを分割して動かせるなら各プロジェクトのタスクキューにタスクを積んでおくだけです。 `takt add` でタスクを追加して `takt run` を実行すれば、あとはTAKTが面倒を見てくれます。

このような体験をもたらすTAKTですが、ほかのオーケストレーションツールとは何が違うのでしょうか。

## ほかのオーケストレーションとの違い

TAKTの立ち位置をもう少し明確にするために、ほかのアプローチとの違いを整理してみましょう。

### AIの自由度をあえて排除する

マルチエージェントのオーケストレーションは、TAKTだけが取り組んでいるわけではありません。さまざまなツールやフレームワークが存在します。

しかし、TAKTの思想は少し異なります。皆さんはどちらのアプローチがお好みでしょうか。

多くのオーケストレーションシステムは、AIに自由度を与える方向に向かっています。AIが自分で判断して、必要なエージェントを呼び出し、必要なツールを使う。賢いAIであれば、それがうまくいく場面もあるでしょう。

TAKTはその逆です。AIの自由度をあえて排除して、定義されたピースに従わせることに特化しています。

なぜか。冒頭でお話ししたとおり、AIに自由に判断させると、やってほしいことをやってくれないからです。レビューをスキップしたり、サブエージェントを呼び忘れたり。AIの判断力を信じるのは素晴らしいことですが、実務で必要なのは再現性と確実性です。

TAKTは「AIを信頼しつつ、仕組みで担保する」というアプローチを取っています。

### Claude CodeのSwarmとの違い

Claude CodeではSwarmという仕組みも登場しています。Swarmは複数のエージェントが協調して作業を進める仕組みのようですが、TAKTとはおそらく異なるものだと考えています。

Swarmはエージェント間の動的な協調に重きを置いているように見えます。それに対して、TAKTは事前に定義されたピースの確実な実行に重きを置いています。

どちらが優れているというものではありません。用途が違います。探索的な作業、創造的な問題解決ではSwarmのような自由度の高いアプローチが向いているのではないでしょうか。一方、決まった品質基準でコードを書き、レビューし、修正するという定型的な開発フローでは、TAKTのような強制力のあるアプローチが合っていると思います。

## まとめ

TAKTは、AIエージェントに「強制力のあるピース」を与えることで、マルチエージェント開発の再現性と品質を担保するツールです。

AIエージェントが言うことを聞かない。せっかく用意したツールを使ってくれない。進捗を見張るのに疲れた。そんな経験がある方は、ぜひTAKTを試してみてください。

タスクを投げたら、あとはTAKTに任せる。指揮者がタクトを振るように、AIエージェントたちが協調して動き出します。

TAKTはOSSとして公開しています。バックエンドはClaude CodeやOpenAI Codexなので、普段これらを使っている方であれば、そのままTAKTで束ねて使えます。API Keyがあれば、CLIをインストールしなくても使えます。

```
npm install -g takt
```

TAKTはまだまだ開発中です。私自身が毎日のように使っているので、「ここが不便だな」「こんな機能があったらいいな」という気づきが日々出てきます。それをそのまま機能として実装していくので、これからどんどん多機能化していく予定です。

皆さんの開発体験が少しでも快適になれば嬉しいです。

実をいうと、OSSとして公開するのは初めてに近い経験です。もしやり方が間違っていたり、お作法がなっていない部分があったりしたら、すみません。温かい目で見守っていただけると助かります。

ちなみにTAKTはTAKTで作られています。ピースはdefaultを使っています。

## おまけ　MAGIシステムでエヴァごっこ

複数のAIといえば、やっぱりエヴァンゲリオンですよね。

TAKTには「MAGI」という機能が搭載されています。エヴァンゲリオンに登場するMAGIシステムにインスパイアされた審議システムです。実際にみてみましょう。

MAGIシステムでは、3つのペルソナが異なる視点からお題を分析して投票します。

- MELCHIOR-1（Scientist / 科学者）　論理的・データ駆動の視点で判断
- BALTHASAR-2（Nurturer / 育成者）　チームや人間を中心に考える視点で判断
- CASPER-3（Pragmatist / 現実主義者）　実用的・現実的な視点で判断

この3つのペルソナがそれぞれ独立に判断を下し、多数決で最終的な結論が導かれます。

技術的な意思決定を多角的に検討したいときに、magi を使えばエヴァごっこをしながら合理的な判断ができます。せっかくAIを複数動かすなら、こういう遊び心があってもいいのではないでしょうか。

「MELCHIOR、承認」「BALTHASAR、承認」「CASPER、条件付き承認」

こんな具合に、複数の視点からの判断結果が得られるわけです。楽しいですよね。

実用と遊び心の両立。それもTAKTの魅力の一つだと思っています。

ぜひ、TAKTで皆さん自身のAIオーケストラを指揮してみてください。

## さいごに

ここまで読んでくださった皆さんなら想像ついたでしょうか。

実はこの記事自体が、TAKTを使って書かれています（もちろん手直しはいれていますが）。つまり、TAKTで書いた記事でTAKTを紹介しているわけです。

著者エージェントが文章を執筆し、専門知識レビュアーエージェントが技術的な正確性をチェックし、編集エージェントがスタイルガイドに沿った文体になっているかを確認する。指摘があれば著者エージェントが修正し、再びレビューを受ける。そのピースを何度か回した結果が、皆さんが今読んでいるこの記事です。また、各エージェントは私が書いた書籍や記事を学習しています。

もし「この記事、読みやすいな」と思っていただけたなら、それはTAKTのピースがうまく機能した証拠かもしれません。逆に「ここ、ちょっと変だな」と思った箇所があれば、それはピースの改善ポイントです。次の記事ではもっとうまくやれるでしょう。

とはいえ、残った地獄が一つあります。人の目によるレビューです。

AIが書いてAIがレビューしても、最終的に人間が読んで「これでいいか」を判断する工程だけは、どうしても避けられません。この記事も、TAKTが出力した文章を私が読み直して手を入れています。ここだけは今のところ自動化できていないのです。

なんとかしたいですよね。というわけで、また何か作ると思います。

TAKTは、コードだけでなく文章も書けます。皆さんもぜひ、いろいろな使い方を試してみてください。
