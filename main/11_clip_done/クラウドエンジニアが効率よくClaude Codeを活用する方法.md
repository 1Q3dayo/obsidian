## クラウドエンジニアが効率よく Claude Code を活用する方法

## はじめに

2026 年以降、AI コーディングツールの普及が加速する中、Anthropic の Claude Code はターミナル上でファイルの読み書きからコマンド実行、Git 操作まで自律的に行える点が特徴です。

Web 上には、アプリ開発者向けの情報は多い一方で、 **「クラウドエンジニアとして」どう使いこなすか** という観点の情報はまだ少ないこともあり、本記事では、IaC 生成、アーキテクチャ設計、運用といった、クラウドエンジニアの業務に絞って、Claude Code を効率よく使いこなすための実践的なノウハウを解説します。

---

## 1\. CLAUDE.md の設計が成否を分ける

Claude Code 活用における最重要設定をファイルに書き出したのが `CLAUDE.md` です。プロジェクトのルートに置くことで、Claude Code がセッション開始時に読み込むコンテキストとして機能します。

### 1-1. CLAUDE.md に書くべき内容

クラウドエンジニアの場合、以下のように記載すると効果的です。

```
# プロジェクト概要
[サービス名] の AWS インフラを Terraform で管理するものです。

# 技術スタック
- IaC: Terraform 1.14.x
- クラウド: AWS
  - リージョン: ap-northeast-1
- 状態管理: S3 バックエンド

# ディレクトリ構成ルール
- 環境別ディレクトリ分割
  - 開発: dev
  - 検証: stg
  - 本番: prod
- modules/ : 再利用可能なモジュール
- envs/    : 環境別設定
  - 開発: envs/dev/
  - 検証: envs/stg/
  - 本番: envs/prod/
- .tfvars は envs/ 配下に環境別で管理

# 命名規則
- リソース名: {env}-{service}-{resource-type}
  - 例: prod-api-sg
- タグは必須
  - Env
  - Service
  - ManagedBy=terraform

# 禁止事項
- terraform apply を直接実行しない
  - ユーザによる実行
  - CI/CD 経由のみ
- ARN・アカウント ID はハードコーディングしない
  - アカウント ID は data.aws_caller_identity で動的に取得すること

# 参照先ドキュメント
- アーキテクチャ: docs/architecture.md
- 命名規則詳細: docs/naming-convention.md
```

### 1-2. CLAUDE.md 設計の注意点

CLAUDE.md ファイルは Claude Code のセッション開始時にコンテキストに読み込まれます。Git の PR レビューやデータベース移行といった「特定のワークフロー用の詳細な指示」を含める場合など、関連のない作業を行っている場合でもそれら用のトークンが存在・確保することになります。

そのため、

- **500行以内・必須事項のみ** に絞る。
	- 詳細な手順は別ファイルに切り出す。
- **CLAUDE.md はインデックスとして扱う** 。
	- ありとあらゆるルールや実装方法を詰め込まない。
		- コンテキストウィンドウの逼迫による性能劣化や内容が無視されるといった挙動につながる
- 特定フローの詳細手順は **Skill（オンデマンド読み込み）** として切り出すとよい。
	- ベースコンテキストを小さく保てる。

## 2\. コンテキスト管理の実践

### 2-1. コンテキストは「ディスク容量」として管理する

コンテキストウィンドウ内のトークン量が増えるにつれ、モデルのパフォーマンスは劣化していく傾向があります。また、推論が必要なタスクについてはその傾向がより顕著になるとされています。つまり **「まだトークンに余裕がある」＝「使い続けて良い」わけではない** ということです。

**おすすめの管理サイクル**

```
タスク開始
 └→ /context でトークン残量を確認
 └→ 70% に達したら /compact で圧縮
 └→ 別タスクに切り替えるときは /clear でリセット
```

### 2-2. Plan Mode (実装プラン策定) の活用

Plan Mode を使うと、 **実装プランを立てるセッションと実装するセッションを分ける** ことができます。新しい綺麗なコンテキストウィンドウで、具体的な実装計画を基に実装することで、パフォーマンスが劣化してないモデルの一番性能の良い部分を、実装フェーズに充てることができるようになります。

クラウドエンジニアの活用方法に当てはめると、

- Plan セッション / 実装プラン策定
	- 依頼： 「このマイクロサービス構成を ECS Fargate に移行する手順を設計して、現行構成は @docs/current-arch.md を参照」
		- 移行手順・Terraform 変更箇所・リスクをまとめさせる。
- Implement セッション / 実装プラン実行 （新しいコンテキストで開始）
	- 依頼： 「先ほど作成した移行計画に従って、modules/ecs\_service/main.tf を修正して」
		- パフォーマンスに影響が何もない、クリーンな状態で実装に集中させる。

## 3\. クラウドエンジニア特有の活用パターン

### 3-1. IaC 生成：設計意図を先に固める

- **重要**
	- Claude Code に Terraform を書かせる場合、 **いきなりコードを要求するのはアンチパターン** です。
- ❌ アンチパターン：いきなり実装を要求。
	- 「MySQL を RDS で作って欲しいです。Terraform で書いて」

Claude Code を使いこなすためには、システム開発と同様に段階的なフェーズを経るアプローチが効果的です。

- ✅ 推奨パターン：設計判断を先にさせる。
	- 「以下の要件で RDS 構成を設計して」
		- 要件例: MySQL 8.0 / マルチAZ / 本番用 / コスト最適化優先
		- どのインスタンスタイプが適切か（コスト考慮）
		- スナップショット・バックアップ設計（運用設計）
		- セキュリティグループの設定（通信設計） etc...
		- 「まずは設計判断の根拠を出しながら確定をさせたいです。コードを書くのはその後にして」
- ✅ 推奨パターン（特定の対応時）：新規設計・大きめの方針変更時に推奨。
	- アーキテクチャ・設計は Claude チャットアプリ、実装は Claude Code と役割を分担させる。
		- **Claude チャットアプリの方で議論して、要件を元にしたアーキテクチャ・設計を確定させる。**
		- 「以下の要件で RDS 構成を設計して」
			- 要件例: MySQL 8.0 / マルチAZ / 本番用 / コスト最適化優先
				- どのインスタンスタイプが適切か（コスト考慮）
				- スナップショット・バックアップ設計（運用設計）
				- セキュリティグループの設定（通信設計） etc...
				- 「アーキテクチャと設計が確定したら Markdown 形式で詳細をまとめてください」
		- **確定した詳細資料を元に Claude Code で実装していく。**
		- 「事前に確定させたアーキテクチャ・設計の資料があるので、それを元に Terraform の tf ファイルにコードを書いて」
		- この方式の最大のメリットとして、
		- **無駄なトークン消費量を可能な限り減らす**
			- Claude Code との議論は実装時の現実的なものに限定させる。
				- **反応待ち時間の短縮**
			- Claude Code はコールアンドレスポンスの観点から数十秒〜数分の待機時間が発生しがち。
				- Claude チャットアプリの方はそれらの待機時間がほぼないため、効率よい議論を展開できる。
		- ただし、注意点として、
		- 既存の Git 連携をベースとしたやり方を前提とするなら Claude Code のみ限定が効率的
			- 理由：git diff による差分確認・比較や、既存 tf ファイルなどのコード群を参照できるため
				- 大雑把な内容や前提条件をまとめていく方式として推奨される。

複雑な実装はいきなり全部やらせるのではなく、以下 2 点を考慮すべきです。

- まず既存コードを把握させ、全体像を考えさせ、タスクを小さく分解するという段階的なアプローチが有効。
- 情報を資料化させておいて (Markdown で OK)、全体像とタスクを把握させることで、対応箇所が具体的かつ明確化されるアプローチが有効。

### 3-2. アーキテクチャレビュー：観点を明示して精度を上げる

以下のように「一括で情報をまとめたチャットを投げる」ことで精度の向上が期待できます。

```
以下の観点で現状の Terraform 構成をレビューして
 * セキュリティ（セキュリティグループの過剰な開放 / IAM の最小権限違反）
 * コスト最適化（オーバースペック / 不要リソース）
 * 可用性（単一障害点 / マルチAZ 未対応）
 * Terraform ベストプラクティス準拠
 対象: @modules/vpc/
```

Claude Code は git diff を自動で実行し、変更差分を読み取ったうえで指摘してくれます。型の不整合や変数の使い方・考慮漏れなど、人間による目視では見落としがちな点を拾ってくれるメリットは大きいです。

### 3-3. 運用ドキュメント生成：コードから逆引き

```
envs/prod/ 配下の全 .tf ファイルを読み取って、以下を Markdown で生成して
 * リソース一覧（種別・名前・用途）
 * ネットワーク構成のサマリ
 * セキュリティグループの許可ルール一覧
```

IaC の概念として「構築済み環境」と「適用したコード」は等しい前提であり、Claude Code を活用すると既存コードをベースに、乖離しないドキュメントを即座に生成できるため、インフラ変更のたびに手動でドキュメントを更新する手間を大幅に削減できます。

## 4\. トークン消費を抑える実践テクニック

### 4-1. Claude Code 単体でのモデル使い分け

日常作業は Sonnet 4.6 で十分であり、/model コマンドでセッション中に切り替えられます。

クラウドエンジニアが活用していく前提での使い分け目安としては、

| タスク | 推奨モデル |
| --- | --- |
| 既存 tf ファイルの修正・追記 | Sonnet 4.6 |
| セキュリティレビュー | Sonnet 4.6 |
| 複雑なマルチアカウント設計 | Opus 4.6 |
| 大規模移行の方針策定 | Opus 4.6（思考モード） |
| 簡単なリソース名生成・確認 | Haiku 4.5 |

### 4-2. Claude チャットアプリ併用時のモデル戦略

Claude チャットアプリを併用することで、更にトークン消費を抑えることが可能です。

- Claude チャットアプリ
	- 複雑かつ難しいタスク: Opus 前提
- Claude Code
	- 実装タスク: Sonnet で十分

使い分け目安としては、

- Claude チャットアプリ

| タスク | 推奨モデル |
| --- | --- |
| 要件定義 | Opus 4.6 |
| アーキテクチャ・設計議論 | Opus 4.6 |
| セキュリティ設計 | Opus 4.6 |
| 運用設計 | Sonnet 4.6 |

- Claude Code

| タスク | 推奨モデル |
| --- | --- |
| tf ファイルの作成・修正 | Sonnet 4.6 |
| コードレビュー、セキュリティレビュー | Sonnet 4.6 |

### 4-3. 不要な出力を抑制する

Sonnet 4.6 以降、出力が冗長化する傾向があります。Dockerfile のビルド手順の Markdown ファイル出力やデプロイ手順の解説など、不要なドキュメントを自動生成しがちです。

`.claude/settings.json` で書き込みを制限しておくと安全です。

```
{
  "permissions": {
    "deny": [
      "Write(./docs/**)",
      "Write(./documentation/**)",
      "Write(README.md)"
    ]
  }
}
```

また、環境変数で不要な処理を無効化することも有効です。

```
# 自律的な不要なモデル呼び出しを抑制
DISABLE_NON_ESSENTIAL_MODEL_CALLS=true

# 出力を簡潔に
outputStyle: "Concise"  # settings.json で設定
```

## 5\. やりがちなアンチパターンまとめ

| アンチパターン | 問題点 | 対策 |
| --- | --- | --- |
| CLAUDE.md に全ルールを詰め込む | コンテキスト圧迫・内容が無視される | インデックスに留め、詳細は別ファイルへ |
| 長いセッションで /clear しない | Context Rot でアウトプット品質が低下 | タスク区切りで必ず /clear |
| 「いい感じに書いて」みたいな曖昧な指示 | 冗長なコード・不要なドキュメント生成 | スコープ・ファイルパス・条件を明示的に指示・指定 |
| Opus を常時使う | 過剰なコストが発生する | 日常作業は Sonnet で十分 |
| 大きなタスクを一度に渡す | 既存構成を無視した実装になりやすい | Plan（実装プラン策定） → Implement（実装）と、段階的に行う |
| 思考モードを常にフル活用 | 思考トークンは出力トークンとして課金されるため、単純なタスクではコストが膨らむ | 複雑な設計時だけ Opus + 高思考モードに切り替える |

## 6\. まとめ

クラウドエンジニアとして Claude Code を効率よく使いこなすためのポイントを振り返ります。

- **CLAUDE.md はインデックス** として設計し、プロジェクト固有のルールを500行以内で凝縮する。
- **Plan（実装プラン策定） → Implement（実装）の 2 セッション分割**
	- コンテキストをクリーンに保ち、アウトプット品質を安定させる。
- **IaC 生成は設計判断を先に固めてから実装させる。** いきなりコードを要求しない。
	- Claude チャットアプリの併用で、役割分担をさせる方法を最も推奨。
		- Claude チャットアプリ: 設計
				- Claude Code: 実装
- **モデルは使い分ける** 。日常は Sonnet 4.6、複雑な設計や難しめのタスクは Opus 4.6 に切り替える。
	- 既存コードを参照・変更といった点が不要の場合、Claude チャットアプリ併用も効果的。

Claude Code は **「とりあえず使える」段階から、「意図通りに動かせる」段階に到達するまでのギャップがかなり大きいツール** です。 **「なんとなくの雰囲気で使う」のと「ベストな活用方法を理解できている前提で使う」のとでは比較にならないほどの差が出ます。**

今後のクラウドエンジニアの業務において、Claude Code に限らず、AI コーディングは「主流になって使うのが当たり前」になっていくものと思われます。効率良い Claude Code 活用のため、CLAUDE.md の整備とコンテキスト管理を起点に、チームの運用に合わせた使い方を磨いていきましょう。
