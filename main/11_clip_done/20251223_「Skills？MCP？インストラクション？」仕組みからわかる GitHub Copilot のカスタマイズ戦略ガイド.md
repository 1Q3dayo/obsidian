## はじめに

2025 年、GitHub Copilot は Agent Mode の登場とともに大きく進化しました。それに伴って、Agent Skills、MCP (Model Context Protocol)、カスタム インストラクション、カスタム エージェント、カスタム プロンプトといった多様なカスタマイズ方法が次々と登場し、開発者は「選択肢が多すぎる！」という嬉しい悲鳴を上げています。

- 「Agent Skills がいいらしいけど、これまでのカスタムインストラクションとどう違うんだ？」
- 「MCP と Agent Skills、どっちを使えばいいの？」
- 「それぞれどう使い分けたらいいの？」

特に Agent Skills は 2025 年 12 月 18 日に提供が開始されたばかりで、情報も錯綜しています [^1] 。

そこで、本記事では、GitHub Copilot のカスタマイズ手法を「LLM の仕組み」から深掘りし、各手法の動作原理と最適な選択基準を解説します。単なる「使い方」ではなく、「なぜそう動くのか」「なぜその選択が最適なのか」を理解することで、今後新しいカスタマイズ方法が登場しても応用できる力を身につけましょう。

## そもそも AI アプリはどうやって動いているのか？

まずは、AI アプリケーションが LLM をどのように利用しているか、基本的な仕組みを押さえましょう。

### メッセージベースのやり取り

LLM は、システムメッセージ、ユーザーメッセージ、ツールメッセージ、アシスタントメッセージの 4 種類のメッセージを入出力する装置です。それぞれの役割は以下の通りです。

- **システム メッセージ (system)**: モデルの振る舞い（指示）や背景情報
- **ユーザー メッセージ (user)**: ユーザーからの入力
- **ツール メッセージ (tool)**: LLM が外部ツールを呼び出す際に使用するメッセージ
- **アシスタント メッセージ (assistant)**: LLM が生成する応答

LLM は、これらのメッセージのリストを入力し、次のメッセージ（tool/assistant）を出力します。AI アプリケーションは、メッセージリストを更新（主に追記）しながら LLM とのやり取りを繰り返すことで、対話やタスクを実現します。

また、入力のメッセージリストは **コンテキスト (context)** と呼ばれます。コンテキストは、LLM の応答品質に大きな影響を与えることが知られており、適切な生成・更新戦略が求められます。コンテキスト生成にまつわる技巧や工夫を **コンテキスト エンジニアリング (context engineering)** と総称します。

コンテキスト エンジニアリングが必要な理由は、「雑にコンテキストを作ると LLM の応答品質が悪くなる」ことが経験的に知られているからです。間違ったツールを呼び出したり、ハルシネーションを起こす確率が高くなったりします。これらの問題を避けるために、 **「何をコンテキストに含めるか」** と **「何をコンテキストに含めないか」** の決定がとても重要です。

すこし抽象的な説明が多くなってしまったので、天気予報の結果を返す MCP ツールを例に、これらのメッセージがどのようにやり取りされるか具体的に見てみましょう。

### 例: 天気予報 MCP ツールを使ったやりとり

まず、ユーザーがクライアントアプリに「明日は晴れですか？」と質問します。

![](https://storage.googleapis.com/zenn-user-upload/af56a0a5ff25-20251221.png)  
*ユーザーが「明日は晴れですか？」とクライアントアプリに質問する*

クライアントアプリは、この質問を LLM の入力に変換します。LLM の入力は、大きくメタデータとメッセージリストに大別できます。

- **メタデータ**: モデル、最大のトークン数、ツール定義など
- **メッセージリスト**: これまでのメッセージのやり取り

メッセージリストを構築する際は、単にユーザー質問だけを含めるのではなく、LLM がより適切に応答できるような工夫（コンテキストエンジニアリング）をします。具体的には、システムメッセージを追加することが、この工夫に当たります。

システムメッセージに何が含まれるかは、クライアントアプリに依存します。たとえば、この仮想的なクライアントアプリは次の機能をサポートしているとします。

- カスタム インストラクションの追加
- ビルトイン ツールでのコマンド実行
- 天気予報の情報を取得する MCP サーバーの登録
- ユーザーの過去の言動の記憶（メモリー機能）

すると、おそらく以下のようなメッセージリストが生成されるはずです。

![](https://storage.googleapis.com/zenn-user-upload/386db987306a-20251222.png)  
*クライアントアプリがメッセージリストとメタデータを構成し、LLM に入力する*

一定の賢さを持った LLM であれば、この入力を受け取ると `get_waether` ツールを呼び出す必要があると判断するでしょう。そこで、LLM は以下のようなメッセージを返却します。

![](https://storage.googleapis.com/zenn-user-upload/bdcdf2944e6c-20251222.png)  
*LLM が `get_weather` ツールを呼び出すためのツールメッセージを生成して返す*

クライアントアプリは、メッセージの通り MCP サーバーにリクエストを送信します。ここで、クライアントアプリがツール呼び出しできるように、リクエストのパラメータは（メタデータに記載されたツール スキーマに基づいて）構造化されています。こうした動作は [Structured Outputs](https://openai.com/ja-JP/index/introducing-structured-outputs-in-the-api/) と呼ばれます。

![](https://storage.googleapis.com/zenn-user-upload/35e22d70ce71-20251222.png)  
*クライアントアプリが、Weather MCP にリクエストを送信する*

MCP サーバーから `{"temperature": "15°C", "condition": "晴れ"}` のような結果が返ってきたら、メッセージリストを更新します。先ほどまでのやり取りに加え、ツールの実行結果を加えたメッセージリストを作成して、LLM に入力します。

![](https://storage.googleapis.com/zenn-user-upload/4cf14cb74823-20251222.png)  
*クライアントアプリがツール実行結果を含むメッセージリストを LLM に再度入力する*

最終的に、LLM から以下のようなアシスタントメッセージが返されます。これがユーザーへの最終的な応答となります。

![](https://storage.googleapis.com/zenn-user-upload/932484d6de16-20251222.png)  
*LLM が最終的な応答を生成して、ユーザーに返す*

## 天気予報 MCP ツールの例から学ぶポイント

非常に単純化された例ではありますが、この天気予報 MCP ツールの例から、以下の重要なポイントを学ぶことができます。

### ① コンテキスト エンジニアリング = システムメッセージの構築

アプリケーションが調整を頑張れるのは基本的に「システムメッセージ」だけです。ユーザーメッセージやツール呼び出しは制御が難しいためです。したがって、どのようなシステムメッセージをコンテキストに含めるのかがコンテキストエンジニアリングの本質です。

また、何を「含めないか」も同様に重要です。

たとえば、上記の例では `runCommand` というタスクに関係のないツールが含まれていました。LLM にとってみれば、「む、コマンド実行を促されてる・・・？ `get_weather` で十分そうなんだけど・・・」という "迷い" を発生させる原因になります。

コンテキストには、目下のタスクに必要十分な情報（システムメッセージ）だけを含めることが重要です。

### ② 外部環境との接点はツール呼び出し

直接 LLM が外部環境とやり取りすることはありません。すべてツール呼び出しを介して行われます。

ツールは、いわば LLM の手足のような存在であり、これがなければ LLM が主体的に外界とのインタラクションが取れません。観察（外部環境 ⇒ LLM）もできないし、働きかけ（LLM ⇒ 外部環境）もできません。

VS Code のような AI アプリケーションには、通常、ビルトインのツールが用意されており、これによって最低限の外部環境とのインタラクションが担保されていることが多いです。アプリケーションが、カスタムツールを追加する機能 (e.g., MCP サーバーの登録) を持っていれば、さらにツールを増やすことができます。こうしたツールを用いて、適切な手足を用意してあげる必要があります。

## VS Code のコンテキスト管理を理解する

システムメッセージがコンテキスト管理のキーマンであることが分かったところで、VS Code がどのようにメッセージリスト（コンテキスト）を生成するか見ていきます。

もちろん、ユーザーが関与できるのは、明示的なチャネル（オプション、カスタムインストラクション、カスタムエージェント、Skills、・・・）だけなのですが、実はそれ以上に多くの要素があることをここでは示します。

以下に、VS Code のコンテキスト管理の概念図を示します。

![](https://storage.googleapis.com/zenn-user-upload/16242bca03f8-20251222.png)  
*VS Code のコンテキスト管理の概念図*

この図から、多くのコンテキスト管理操作が、直接ユーザーが関与しない形で行われていることがわかります。例えば、

- 閲覧しているファイルをシステムメッセージに追加する
- 呼び出せるツールをすべてメタデータに追加する
- 別のコンテキスト（メッセージリスト）で新たにチャットを始める

といったことが VS Code によって行われています。

ただし、安心してほしいのは、これらの操作がオプションやユーザーのインストラクションによって一定程度調整できるということです。例を挙げると、次のようなものです。

- 閲覧しているファイルを自動的にシステムメッセージに追加してほしくなければ、 `chat.implicitContext.enabled` や `chat.implicitContext.suggestedContext` で OFF にできます。
- ユーザーがツールを選択するか、カスタムエージェントの `tools` 定義を使って、メタデータに記載されるツールを少なくできます。
- `agent/runSubagent` ツールを呼び出す指示を書くことで、新たなコンテキストで特定のタスクを実行することができます。

もちろん、ユーザーが直接影響を与えることもできます。例えば、カスタムインストラクションはその好例です。カスタムインストラクションを記述すると、それがそのままシステムメッセージに変換（追記）されます。

ですが、コンテキスト管理の大部分は上記のように、「設定・仕掛け」⇒「その状況になったら効果を発揮」といった遅延があります。この観点を入れた概念図を描きなおすと、次のようになります。

![](https://storage.googleapis.com/zenn-user-upload/b8054cf07699-20251222.png)  
*ユーザーがコンテキスト管理に直接/間接的に関与していることを示す図*

このセクションの結論としては、今から紹介するような構成・カスタマイズはあくまで表面的なものにすぎず、コンテキスト管理にはいろいろな要素が絡んでいるんだ、ということを持ち帰ってもらえたら十分かなと思います。

## VS Code におけるコンテキスト エンジニアリング手法の整理

それでは、具体的なカスタマイズ方法と、それがどのようにコンテキストに影響するか整理してみましょう。

### ユーザー入力

ユーザーがチャット画面で入力したメッセージや、アタッチしたファイルは、そのままユーザーメッセージ (user) に変換されます。

![](https://storage.googleapis.com/zenn-user-upload/0107a0c84082-20251221.png)  
*VS Code のチャットパネルで入力している様子*

また、エージェントモードやツールも選択することができ、これらはシステムメッセージ (system) に対するメッセージの変化をもたらします。

カスタムエージェントを選択すると、その定義がシステムメッセージに追記されます。これは、 [Chat Debug](https://code.visualstudio.com/docs/copilot/chat/chat-debug-view) でログを見た時に `<modelInstructions>` がシステムメッセージに記載されることから確認できます。

![](https://storage.googleapis.com/zenn-user-upload/21c00827a0f8-20251221.png)  
*modeInstructions ブロックとしてエージェント定義がシステムメッセージに追記されている様子*

また、カスタムエージェントでツールを選択すると、選択したツールのみがシステムメッセージに記載されます。これも Chat Debug で確認ができます。

![](https://storage.googleapis.com/zenn-user-upload/548190c6e44c-20251221.png)  
*指定したツールのみがシステムメッセージに追記されている様子*

こうしたユーザー入力と、モード・ツール選択をパッケージ化して、同じような入力を繰り返し実行するための仕組みが **プロンプト ファイル (prompt files)** です。`.github/prompts/<name>.prompt.md` に記述したユーザーメッセージと選択を、スラッシュコマンド (`/name`) で簡単に呼び出すことができます。後述の通り、プロンプトファイルはエージェントのエントリポイントにするのがお勧めです。

### カスタムインストラクション

追加のシステムメッセージ (system) を生成するためのものが **カスタムインストラクション (custom instructions)** です [^2] 。具体的には、以下の３つの設定箇所のものが、状況に応じてシステムメッセージに読み込まれます（複数読み込まれる）。

| 名前 | 設定ファイルの置き場所 | 説明 |
| --- | --- | --- |
| エージェント インストラクション | `AGENTS.md` | 作業ディレクトリに最も近い `AGENTS.md` を参照し、常にシステムメッセージに追加されます。 |
| repojitory-wide カスタムインストラクション | `.github/copilot-instructions.md` | リポジトリ全体に適用されるカスタムインストラクションで、常にシステムメッセージに追加されます。 |
| path-specific カスタムインストラクション | `.github/instructions/<name>.instructions.md` | 特定のパスに関連付けられたカスタムインストラクションで、特定のパス/拡張子のファイルを操作する際にのみシステムメッセージに追加されます。 |

カスタムインストラクションは単にシステムメッセージを追加するだけなので、ツールを限定することはできません。

### カスタムエージェント

カスタムインストラクションとツール選択をあわせもった性質を持つのが **カスタムエージェント (custom agents)** です。カスタムエージェントは、あらかじめ定義されたシステムメッセージとツールセットを組み合わせて、特定のタスクに最適化されたエージェントを作成する仕組みです。

カスタムエージェントを使用すると、ユーザーはエージェントの名前を指定するだけで、対応するシステムメッセージとツールセットが自動的にコンテキストに組み込まれます。これにより、特定のタスクに対して最適化された応答が得られやすくなります。

### サブエージェント

さらに、カスタムエージェントは別のエージェントから呼び出すことができます。詳細については過去記事 [「GitHub Copilot でカスタムエージェントを runSubagent できるようになったらしい」](https://zenn.dev/openjny/articles/32c8ca30e43c38) を参照してみてください。

サブエージェントとして呼び出されたカスタムエージェントも、親エージェントと同様に独自のシステムメッセージ（エージェント定義、ツールセット）を持ちますが、親エージェントとコンテキストが分離されます。

通常、一つのチャットセッションではコンテキスト（メッセージリスト）は共有され続けるのですが、唯一の例外がサブエージェントの呼び出しです。サブエージェントは親エージェントから独立したコンテキストを持つため、親エージェントのメッセージリストはサブエージェントに引き継がれません。

コンテキストを分離すると得られるメリットには、次のものがあります。

- 呼び出し元での不要なコンテキスト肥大化を防止 (例: ログ調査をサブエージェントで分離)
- 中立的な立場でサブエージェントを実行 (例: レビューエージェントを別コンテキストで実行)

### MCP サーバー

MCP サーバーは、外部環境とやり取りするツールを追加する機能です。Built-in でも、ファイルシステムやターミナル（シェル）とやり取りするためのツールが用意されていますが、さらに外部環境を追加したければ `mcp.json` 等に記述してツールを増やすことができます。

![](https://storage.googleapis.com/zenn-user-upload/8fa638c74355-20251221.png)  
*MCP サーバーの定義ファイル*

実際にユーザーの入力でツールが選ばれる（カスタムエージェント定義で指定される）と、VS Code はツール定義をシステムメッセージ (system) に追加して、LLM が tool メッセージを生成できるようにします。これは、Chat Debug の Metadata セクションを見ると確認できます。

### Agent Skills

Agent Skills は、特定のドメイン知識やタスクに特化したスキル定義をシステムメッセージに自動的に追加する機能です。スキル定義 (`SKILL.md`) を特定のディレクトリ (e.g., `.github/skills/`) に配置することで、自動的にスキル定義へのポインタがシステムメッセージに追加されます。

具体的に、スキル定義は、以下のようなフォーマットの yaml フロントマターを持つカスタムインストラクションファイルです。

SKILL.md

```md
---
name: echo-skill
description: 入力されたテキストをそのままユーザーに返します。
---

# Echo Skill

このスキルは、入力されたテキストを受け取り、それをそのまま返します。
```

このようなファイルを配置しておくと、VS Code は自動的に名前、説明、 `SKILL.md` へのパスをシステムメッセージに追加します（ `# Echo Skill` 以下は追加しない）。これにより、LLM は必要に応じて `SKILL.md` のインストラクションを `read/readFile` で読みにいけるようになり、特定のドメイン知識やタスクに特化した応答が可能になります。

Agent Skills の肝は、こうした遅延ローディングの仕組みを標準化したことです。インストラクションの管理工数が減ることと、エコシステムの発展（e.g. 公開スキルの借用）による恩恵が期待できます。

VS Code が追加するシステムメッセージ

VS Code が追加するシステムメッセージは以下のような形式です。各スキルの名前、説明、（オプショナルの）メタデータ、そしてファイルパスが含まれます。

```
<instructions>
...

<skills>
Here is a list of skills that contain domain specific knowledge on a variety of topics.
Each skill comes with a description of the topic and a file path that contains the detailed instructions.
When a user asks you to perform a task that falls within the domain of a skill, use the 'read_file' tool to acquire the full instructions from the file URI.
<skill>
<name>echo-skill</name>
<description>Echo back the input text.</description>
<file>\project_root\.github\skills\echo\SKILL.md</file>
</skill>
</skills>

</instructions>
```

## よくある質問への回答

以上の点を踏まえ、よくある質問に回答していきます。

### Q1: カスタムインストラクションと Agent Skills の違いは何ですか？

A1: 共通している点は多いです。

- どちらも、システムメッセージを追加する手段です。
- どちらも、ツール（外界とのインタラクション方法）を提供しません。
- どちらも、コンテキストの分離機能を提供しません。

しかし、両者は以下の点で異なります。

- **カスタムインストラクション**: 指示を「直接」システムメッセージに追加します。
- **Agent Skills**: スキル定義ファイルへの「ポインタのみ」をシステムメッセージに追加します。実際の指示は、LLM が必要に応じて `readFile` ツールで読み込みます。

より細かい違いは以下の表をご覧ください。

![](https://storage.googleapis.com/zenn-user-upload/7ef06d6eb69f-20251221.png)  
*カスタムインストラクションと Agent Skills の違い*

### Q2: MCP と Agent Skills の違いは何ですか？

A2: MCP と Agent Skills は、異なるレイヤーで動作するものであり、比較する対象ではありません。

- **MCP**: 外部環境とのやり取りを可能にするためのツールセットを提供します。MCP ツールは、LLM が外部システムとデータをやり取りするための手段です。
- **Agent Skills**: 特定のドメイン知識やタスクに特化したスキル定義を提供します。MCP やビルトインのツールを使いながら、特定のタスクに最適化された応答を生成するための補助的な情報源（インストラクション）とスクリプト群です。

たとえば、多くの Agent Skills がスクリプトをベースにしていますが、これはコマンド実行ツール (`execute/runCommand`) によって外部環境とのやり取りができるからこそ実現できるものです。

外部環境とのやりとりを担保するツール（built-in ツール、MCP ツール）の上に成り立つのが Agent Skills です。

### Q3: じゃあ MCP はこれからもじゃんじゃん使っていくべき？

A3: はい。ただし、Agent Skills とは独立した「MCP ツール利用時の注意点」があるため、以下で説明します。

MCP サーバー登録するとツール定義が読み込まれ、それが自動的にシステムメッセージに追加されます。したがって、ユーザーが認識しない間に、ツール定義がいっぱいになってしまう、というリスクがあります（ツール定義はユーザーが変更できない点に注意）。ツール定義が多すぎると、LLM がどのツールを使うべきか判断しづらくなり、誤ったツールを呼び出す確率が高くなることが知られているため、適切な管理が必要です。

MCP に関する私のガイドラインは次の通りです。

- **なるべくコマンドが良い**: MCP に頼らずとも CLI コマンドできることは、コマンドで実現する（スクリプト化含む）のがお勧めです。理由は以下の２つです。
	- ツール定義を自分でコントロールできる（例: GitHub MCP ではなく `gh` の必要最低限の使い方をカスタムインストラクションか `SKILL.md` に書いておく）
	- ツール実行時のデバッグが容易（例: シェル上の `jq` や `grep` などの操作で、LLM がツール実行にまつわる問題や状況理解をしやすい）
- **統制を取るときは MCP を使う**: 一方で、コマンド実行は自由度が高すぎるため、実行ルールなどを制御することが非常に困難です。セキュアな環境での利用や、チームメンバー内で出来ることを制御したい場合は MCP のほうに利点があがるケースが多いのではないかと思います。
- **MCP でツールを増やすならエージェントでツール選択は必須**: MCP が増えていくとツール定義でシステムメッセージがあふれてしまいます。なるべくツール選択する癖を付けましょう（MCP を使うときに限らない話ではありますが、MCP を使うならなおさら）。

### Q4: タスク特化型の操作をさせたかったら、何をどう使っていくべき？

A4: 目的や状況によって最適な手法は異なりますが、以下のようなガイドラインが考えられます。

**🎯 指針: カスタムエージェントが主体**

基本的に、カスタムエージェントをどう作るか、を考えるべきです。カスタムエージェントを主体におく理由には、次のようなものがあります。

- カスタムエージェントでは、指示とツールセットが両方指定できるため、システムメッセージの省エネ化がしやすい。
- サブエージェントとして呼び出すと、コンテキスト分離できる。
- GitHub Copilot coding agent (GitHub / クラウド) 上で実行できる。
- UI との親和性が高い (エージェント選択や、後述の prompt 呼び出しなどが可能)。

特に、ツールセットが限定できる点やサブエージェント実行できるのはエージェントの大きなメリットです。必要最小限のツールを指定し、LLM が誤ったツールを呼び出すリスクを減らせます。

**🎯 指針: 次に Agent Skills で補強**

スクリプトを書く場合でも、Agent Skills にポートする必要は特になく、基本的にはカスタムエージェントだけでタスク実行は完結します（エージェントにスクリプトの使い方を教えておけば良い）。

しかし、別のカスタムエージェントで再利用したいスクリプトなどがある場合は、それを Agent Skills 化しておくと便利です。

また、自分でスクリプトを書けない、他人の知識を活用したい、という場合も Agent Skills が役立ちます。公開されているスキルを活用することで、ドメイン知識やタスク特化型の操作を簡単に取り入れられます。

### Q5: プロンプト ファイルはどう使うのが良いですか？

A5: プロンプトファイルは、エージェントのエントリポイントに使うのがお勧めです。

以下の記事で詳細に説明していますが、プロンプトはスラッシュコマンド (`/`) で入力しやすい、 `chat.promptFilesRecommendations` でお勧め表示できる機能があります。これを活用して、上記のようなカスタムエージェントに誘導する方法がとても効果的です。

### Q6: まとめると、どう使い分ければ良いですか？

A6: まとめると、以下のような使い分けが考えられます。

| 目的 | 推奨手法 | 理由 |
| --- | --- | --- |
| タスク特化型のエージェントを作成したい | カスタムエージェント | 指示とツールセットを組み合わせて最適化できるため |
| プロジェクトやファイル操作の全体指針をいれておきたい | カスタムインストラクション | 必ずシステムメッセージに追加されるため |
| タスク特化型のスクリプトや知識を共有したい | Agent Skills | スクリプトや知識をスキルとして切り出し、再利用できるため |
| 外部環境とのインタラクション方法をふやしたい | MCP サーバー（注1） | built-in ツールを除けば、MCP ツールが唯一の方法であるため |
| エージェントを簡単に呼び出したい | プロンプトファイル | スラッシュコマンドで簡単に呼び出せるため |

## おわりに

本記事では、GitHub Copilot の各種カスタマイズ手法を「LLM の仕組み」から深掘りし、各手法の動作原理と最適な選択基準を解説しました。

GitHub Copilot は今後も進化を続け、新しいカスタマイズ手法が登場する可能性があります。しかし、LLM の基本的な仕組みとコンテキストエンジニアリングの考え方を理解していれば、新しい手法にも柔軟に対応できるはずです。

今後も GitHub Copilot を活用して、より効率的で効果的な開発体験を追求していきましょう。
